Every change, sealed into a chain you can verify.

A durable, database-agnostic changelog (audit-log) library for Go. It's intentionally git-shaped: stage edits, seal them into content-addressed commits hash-chained to their parents, keep a history per document. Store it all behind a 3-method Log port.

01 quick start

Stage, seal, read back.

One import for the core (standard library only — the package is changelog), one for a backend. Swap the in-memory dev backend for MySQL or ClickHouse later; the Recorder doesn't change.

// go get github.com/zdirnecamlcs96/chronicle/core
// log := changelogmemory.New() — dev/test; swap for a durable adapter in prod

rec := changelog.NewRecorder("invoice-42", log)
rec.Append(changelog.Change{Actor: "alice", Path: "status", Kind: "put", From: "draft", To: "sent"})
commit, err := rec.Commit(ctx, changelog.WithMessage("send invoice"))
// commit.ID = SHA256 over length-framed (parent, message, canonical(changes)), chained onto Head

history, _ := log.Commits(ctx, "invoice-42", 0) // newest-first

03 the mental model

If you know git, you already know it.

Stage with Append, seal with Commit, read with Commits. Each document's history is a branch; Head is its tip. One deliberate divergence: a commit stores At and Authors, but the hash covers only parent, message, and changes — metadata never perturbs the chain, and verification recomputes both the hash and the author set. Retries dedup to a single commit through idempotency keys.

Two git reflexes that deliberately don't exist here: no init (a history begins at its first commit, parent == "") and no working tree (the Recorder's staged buffer is the index). The full side-by-side lives in the git model.

04 two audiences

Store for machines, render for humans.

Change JSON is the commit-hash preimage, so display metadata is never stored — it could not be backfilled, and old history would render blind forever. Instead kit.Explain replays the chain and derives the human form at read time: label trails, keyed-element identity, id → name display values, bookkeeping flags, and per-field ValueNode breakdowns of container values. Declare the schema with the same DiffOptions the write side uses; change them and every existing commit re-renders — no stored byte moves.

rows, _ := chroniclekit.Explain(commits, // oldest-first, same contract as Reconstruct
    chroniclekit.WithArrayKeys(map[string]string{"items": "sku", "items.quantities": "uom"}),
    chroniclekit.WithNameFields("label", "name"))
// rows[i][j] decorates commits[i].Changes[j] — the stored Change rides along untouched

The kit emits structure — slices, names, canonical scalars, flags — never formatting. Separators, truncation, verbs, colors, and folding belong to your renderer: a CLI, a web app, and an email digest can all draw the same rows their own way.

05 architecture

Producers → core → any backend.

Something produces Changes — CRUD handlers, a message consumer, a state diff — a Recorder or the Service facade seals them, and the commit lands in whatever Log you picked. The conformance suite validates every backend against the same contract.

The core stays wire-free. When a Go server wants batteries, the optional kit module layers them on top: state diffing, JSON-Patch conversion, snapshot-backed State/StateAt, read-time Explain display decoration, and kit/httpapi — a ready-made http.ServeMux (POST /commits, GET /commits, GET /commits/{id}, GET /changes) you mount behind your own auth and middleware.

06 backends

Pick a store — or write your own.

Adapters are optional sibling modules; the core never imports one. Implement the 3-method Log yourself and prove it with conformance.RunLogConformance.
