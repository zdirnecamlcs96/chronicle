Every change, sealed into a chain you can verify.

A durable, database-agnostic changelog (audit-log) library for Go. It's intentionally git-shaped: stage edits, seal them into content-addressed commits hash-chained to their parents, keep a history per document. Store it all behind a 3-method Log port.

01 quick start

Stage, seal, read back.

One import for the core (standard library only — the package is changelog), one for a backend. Swap the in-memory dev backend for MySQL or ClickHouse later; the Recorder doesn't change.

// go get github.com/zdirnecamlcs96/chronicle/core
// log := changelogmemory.New() — dev/test; swap for a durable adapter in prod

rec := changelog.NewRecorder("invoice-42", log)
rec.Append(changelog.Change{Actor: "alice", Path: "status", Kind: "put", From: "draft", To: "sent"})
commit, err := rec.Commit(ctx, changelog.WithMessage("send invoice"))
// commit.ID = SHA256 over length-framed (parent, message, canonical(changes)), chained onto Head

history, _ := log.Commits(ctx, "invoice-42", 0) // newest-first

02 what's in the box

Small surface, strong guarantees.

Tamper-evident hash chain

Commit.ID is SHA-256 over length-framed parent, message, and canonicalized changes. Rewrite history and VerifyChain breaks.

One 3-method port

The whole library hangs off Log: AppendCommit, Commits, Head. Implement it and any store becomes a backend.

stdlib-only core

The core module imports nothing beyond the standard library. Database drivers live in the adapters' own go.mods.

Incremental verification

VerifyChainAfter checks only commits past a trusted anchor — no full-chain replay on every audit.

Idempotency keys

At-least-once delivery seals exactly one commit: a retried key returns the original commit instead of a duplicate.

Time travel

StateAt reconstructs a document at any commit, snapshot-backed — O(commits since snapshot), not O(all history).

JSON-Patch interop

The kit module diffs states, converts change batches to and from JSON-Patch, and reconstructs state from history.

Conformance as contract

A backend is correct when it passes the suite — that's what makes “database-agnostic” trustworthy, including for a Log you write.

Graceful degradation

Four optional capabilities — Indexer, Deduper, TailReader, Snapshotter. A backend without them still works.

03 the mental model

If you know git, you already know it.

Stage with Append, seal with Commit, read with Commits. Each document's history is a branch; Head is its tip. One deliberate divergence: author and time stay out of the hash, so the same logical change always yields the same ID — that's what makes retries dedup to a single commit.

Two git reflexes that deliberately don't exist here: no init (a history begins at its first commit, parent == "") and no working tree (the Recorder's staged buffer is the index).

04 architecture

Producers → core → any backend.

Something produces Changes — CRUD handlers, a message consumer, a state diff — a Recorder or the Service facade seals them, and the commit lands in whatever Log you picked. The conformance suite validates every backend against the same contract.

05 backends

Pick a store — or write your own.

Adapters are optional sibling modules; the core never imports one. Implement the 3-method Log yourself and prove it with conformance.RunLogConformance.

BackendModuleConsistencyLog conformanceSerializable append
changelogmemory.New() adapters/memory in-memory · dev/test only, lost on restart ✓ — can fork
changelogsql.Open(…) adapters/sql transactional MySQL · FOR UPDATE + unique constraints ✓ ✓ fork-free
changelogclickhouse.Open(…) adapters/clickhouse eventual · ReplacingMergeTree + FINAL ✓ — no synchronous locks

Choose adapters/sql when concurrent writers must form one linear chain per document; adapters/clickhouse for cheap columnar retention and analytics where producers serialize per document. Operational details — pool tuning, the ClickHouse FINAL cost, migrations, backup/restore — live in OPERATIONS.md.

Read it before you run it.

  • v0, experimental. Pin a specific module version; modules are versioned independently (core/vX.Y.Z, adapters/sql/vX.Y.Z, …).
